# Installing on a client's VM

This is the first-install path for a **brand-new** instance on hardware we do not
already run. It is deliberately separate from `GO-LIVE-RUNBOOK.md`, which
describes updating the existing portal.emsmca.co.za deployment.

Three of these steps did not exist before 2026-07-30 and a fresh install cannot
succeed without them. Each says why.

---

## 0. Prerequisites

- Docker + Docker Compose on the VM
- A PostgreSQL database (managed is strongly preferred — Azure Database for
  PostgreSQL, RDS, etc. — for automated backups and PITR)
- A DNS A record pointing the client's hostname at the VM's public IP
- Ports 80 and 443 open

---

## 1. Configuration

```bash
cp .env.prod.template .env.prod
```

Fill in **every** `CHANGE_ME`. Two of them are generated, not chosen:

```bash
# SECRET_KEY — signs every token in the system
python -c "import secrets; print(secrets.token_urlsafe(48))"

# ENCRYPTION_KEY — set ONCE, never changed, backed up in a password manager
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

> **The backend now refuses to start in production** if either is left as a
> placeholder or is shorter than 32 characters.
>
> This guard exists because neither key fails loudly on its own. `jose` signs
> tokens with any string, and `app/utils/crypto.py` deliberately derives a valid
> Fernet key from any input so that an odd production key cannot brick the app.
> An instance installed from the template unedited would therefore have worked
> perfectly — with a signing key published in our own example file, meaning
> anyone could mint a token claiming SUPER_ADMIN.

Also set `APP_ENV=production`. That flag now controls more than logging: it
stops the **mock scheme server** from being mounted. That router fakes a medical
scheme's OAuth and authorisation engine, answers unauthenticated, and always
approves — it must never sit on a public API next to the real integration.

## 2. Create the database schema

```bash
cd backend
python bootstrap_schema.py            # dry run — reports what it would do
python bootstrap_schema.py --apply
```

> **Do not run `alembic upgrade head` first.** It cannot build this schema from
> nothing. The initial revision (`04be48895f1c`) was autogenerated against an
> already-populated database and committed with an empty body, so on an empty
> database the chain dies on the first `ALTER` with
> `relation "cases" does not exist`. Existing installs never hit this because
> their tables were made by SQLAlchemy's `create_all()` years earlier and the
> version table was stamped by hand afterwards.
>
> `bootstrap_schema.py` creates the tables from the ORM models and then stamps
> Alembic at head. It refuses to touch a database that already has tables or a
> version stamp, so it cannot damage an existing instance.

After bootstrapping, all future releases upgrade normally:

```bash
alembic upgrade head
```

---

## 3. Render the nginx config for the client's domain

```bash
PORTAL_DOMAIN=portal.client.co.za \
PORTAL_HOST_IP=203.0.113.10 \
PORTAL_ADMIN_EMAIL=admin@client.co.za \
bash deploy/scripts/render-nginx.sh
```

> `nginx/nginx.conf` hardcoded `portal.emsmca.co.za` — in `server_name` **and**
> in both `ssl_certificate` paths. On any other VM nginx starts, fails to find
> `/etc/letsencrypt/live/portal.emsmca.co.za/fullchain.pem`, and exits. The
> whole site is down and the reason is buried in a container log.

---

## 4. Issue the TLS certificate

nginx will not start without the certificate the rendered config references, so
issue it before the first full `up`:

```bash
docker compose -f docker-compose.prod.yml run --rm ems_certbot \
  certonly --webroot -w /var/www/certbot \
  -d "$PORTAL_DOMAIN" --agree-tos -m "$PORTAL_ADMIN_EMAIL"
```

---

## 5. Start the stack

```bash
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml exec ems_nginx nginx -t
```

---

## 6. Create the first administrator

Seeding is disabled outside development, so there is no default account and no
default password to change. Create the first SUPER_ADMIN explicitly:

```bash
cd backend
python create_admin.py        # if present; otherwise insert via the app shell
```

## 7. Post-install verification

Run these before handing over. Each corresponds to something that was actually
broken.

```bash
# The invoice submit endpoint must require authentication (it had none)
curl -si -X POST https://$PORTAL_DOMAIN/api/invoices/00000000-0000-0000-0000-000000000000/submit \
  | head -1                                     # expect 401

# The wipe-everything route must be closed to anonymous callers
curl -si -X DELETE https://$PORTAL_DOMAIN/api/cases/all | head -1   # expect 401

# The mock scheme server must not be mounted
curl -si -X POST https://$PORTAL_DOMAIN/api/mock-scheme/oauth/token | head -1  # expect 403/404

# API docs must not be public
curl -si https://$PORTAL_DOMAIN/docs | head -1          # expect 403
curl -si https://$PORTAL_DOMAIN/openapi.json | head -1  # expect 403

# Health
curl -s https://$PORTAL_DOMAIN/health
```

## 8. Still owner-supplied (not automatable here)

These are deliberately left to whoever owns the client relationship:

- `AZURE_SAS_URL` — arms the off-site backup copy. Until it is set, backups
  exist only on the VM.
- `HEALTHCHECK_URL` — arms alerting. Until it is set, a failed backup is silent.
- Escrow of the client's `.env.prod` (particularly `ENCRYPTION_KEY`, which
  cannot be regenerated without losing what it protects).
- A **test restore** on the client's own database before go-live. Backups that
  have never been restored are not backups.

## Roles, so access is granted correctly on day one

`require_role` treats `SUPER_ADMIN` as satisfying every check, so a super admin
needs no additional grants. Everything else is least-privilege:

| Role | Notes |
|---|---|
| `SUPER_ADMIN` | Everything, including `DELETE /api/cases/all`. Give to one or two people. |
| `ADMIN` | Provider management, invoice submission, user management. |
| `DISPATCHER` / `PARAMEDIC` / `BILLING_CLERK` | **`PARAMEDIC` is the default role for a new account.** It has no provider-administration access. |

> Until 2026-07-30, "authenticated" was effectively "privileged": a default
> `PARAMEDIC` account could administer every provider on the instance — set the
> portal password that unlocks crew devices, read SMTP credentials, obtain
> plaintext temporary passwords, and page through another tenant's PRF history.
> On a single-tenant box that was survivable. On a shared client VM it made one
> back-office login a master key for every tenant.
